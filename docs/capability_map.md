# Capability Map

**What this is for:** the other two docs are indexed by *module*. `architecture.md`
answers "what is `src/foo.py`?" and `user_guide.md` answers "what can I do from
Discord?". Neither can answer **"what already implements capability X?"** — so
when a capability gets built a second time, nothing in either doc looks wrong.
The new module simply gets a new section.

This file is the inverse index: capability → implementations. Its job is to make
a second implementation *visible* at the moment someone adds one.

**Read this before building anything that parks, schedules, stores, notifies,
retries, or spawns.** Search by intent, not by name — a re-derived implementation
never shares the name of the original (DP-302).

**Verdict column:**

- `single` — one owner. Reuse it.
- `by design` — several implementations, deliberately, with a recorded reason.
  Adding a third needs the same bar: a decision record, not a preference.
- `unreviewed` — several implementations, no recorded decision. Not automatically
  wrong; nobody has ruled. These are the audit queue.
- `single mechanism, one implementation outstanding` — the convergence was decided
  and built, but a known re-derivation has not migrated onto it yet. **Reuse the
  mechanism; do not copy the straggler.** The row names it and the ticket that
  retires it. Distinct from `by design` — nothing here is deliberate — and distinct
  from `unreviewed`, where nobody has ruled at all. A plain `single` on a capability
  with a live second implementation is the failure mode this verdict exists to
  prevent: it reads as "done" to the next author.

Keep rows sorted by capability. When you add a capability, add a row. When you
add a *second* implementation of an existing capability, change the verdict to
`by design` and link the decision — or don't write it.

This verdict returns to plain `single` when it lands. **Read this row before adding anything that waits for an external event to answer a tool call.** It was FOUR implementations: the DP-297 approval park (the correct one), `self_edit/integration._wake_fixr` (DP-227), and DP-343's `JobCompletionBridge` serving both the node install ping and the cold-tier promotion. The mechanism had existed since DP-297 — the constant proving where it belongs was in the *tool loop*, not the approval subsystem — but every name on it said "write" and "approval", so neither later author recognized it. ⚠️ **The anti-duplication control fired here and still missed.** DP-343 added a capability-map row ("Wake a persona on a non-user event") and recorded `by design`, but compared itself against `_wake_fixr`, the shallow sibling; the deep sibling (durable record → exactly-once take → rendered nudge → resumed turn) was not in the row at all. **Comparing against the wrong sibling makes `by design` read as considered when it was not** — when filling that column, search for the implementation with the most shared *mechanism*, not the most similar *description*. What the re-derivations each rebuilt: resume coordinates (from **config**, via five env vars naming a persona/channel/user the row already carried), exactly-once (an in-process `OrderedDict` lost on restart, versus a row claim), nudge rendering, and the entry into the turn — and that last one was a live bug: entering via `generate_response` means `continuation is None`, so `_orchestrate` **persisted the whole synthetic wake message as a durable user row**. Introduced DP-297: with N proposals resolvable at once, two approvals would otherwise run two tool loops over the same history, each writing its own assistant row. Guarantees serialization; folding several decisions into one summary is best-effort (an uncontended lock does not suspend, so the winner is usually already inside its continuation). |
| Decide whether a call needs approval | `definitions.is_write_tool()` — tool-loop universal write audit (registry `is_write`; the import-time `WRITE_TOOLS` set is **gone**, DP-268) · `mcp_bridge._is_gated` (`is_write` OR `capabilities.irreversible`) · `definitions.is_irreversible()` + `tools/classifiers.py` argument-aware reversibility · `definitions.ALWAYS_CONFIRM_TOOLS` (name-keyed strictest tier, defined `definitions.py:174`, consumed by `tool_loop.py:511`) | `by design` — **composition, not one list**, resolved DP-306. Four predicates asking genuinely different questions ("is it a write" / "does it cross the agent trust boundary" / "is it irreversible *for these arguments*" / "is it confirm-always"), but all now derive from one declaration source: the tool definition's `is_write` + `capabilities` block. `validate_tool_capabilities` rejects a callable tool that omits `is_write`, so an unclassified tool **cannot register** — a stronger gate than a test. Non-`function` entries (engine signals like `google_grounding`) are explicitly exempt. Differential audit over all 45 tools found **zero disagreement**; `tests/tools/test_tool_definitions.py` pins the predicates to each other and fails if they drift. |
| Ask a running subagent a question | `self_edit` `answer_agent` tool + `AgentRecord.status == waiting` | `single` |
| Decide whether a tool call **failed** | `tool_manager.tool_error()` — consumed by `tool_loop._execute_calls` (colours `ToolCallResultEvent.error` / the portal ToolCard) and by `ConfirmationManager.apply` (derives `Decision.ok` → `approved_but_failed` in durable history + `executed_ok` in the audit row) | `single` since DP-323. Was two re-derivations of `result.get("error")`, one per consumer, and **both were wrong the same way**: `execute_tool` wraps a normal return as `{"result": <payload>}`, so the seven gated writes that report failure by *returning* (`{"status": "error"}` — every proxmox write + `dispatch_fix`; `{"executed": False}` — `approve_proposal`, which catches its executor's exception by design and therefore *cannot* raise) sat one level below where both looked. On the tool-loop side that mis-coloured a card; on the write-gate side a failed irreversible write was recorded as `approved` with `executed_ok=True`. Deliberately narrow — over-reporting is the dangerous direction, because a successful irreversible write marked failed invites the model to re-propose it. **A new handler must raise or use one of the recognized markers; a third failure idiom will be read as success.** |
| Surface an internal failure to the user | `generation_events.format_internal_error` — exception class + one-line scrubbed detail + an 8-hex `ref`, logged as `[err <id>]` beside the traceback. Those two Discord sites replied with the fixed string *"A critical error occurred. Please check the logs."* — no class, no detail, no id to grep by. That is what a second implementation of this capability looks like when it is written as a literal rather than a function: no clone detector finds it, the capability map had no row to check it against, and a `PermissionError` that had broken every persona-mutating command sat undiagnosed for two weeks behind it. ⚠️ **Remaining gap, deliberately out of DP-362's scope:** `gmail_bot._handle_specific_message` and `_process_new_events` catch and *only log* — the sender is told nothing at all. Converging those means deciding what an error reply over email should look like, which is a product question, not a refactor. |

## Authorization

| Capability | Implementations | Verdict |
|---|---|---|
| Match an origin against an allowlist | `origin.parse_operator_allowlist` + `origin.is_discord_operator` (`server_id[/channel_id[/author_id]]`, `*` wildcards, malformed entries dropped so a typo narrows and never widens) | `single` — one parser and one matcher, shared by both gates below. | Decide whether an origin may run a control-plane command | `message_handler.BotLogic.preprocess_message` — `CONTROL_PLANE_COMMANDS` gate on `Origin.operator` (DP-277) | `single` — deny-by-default at dispatch for the whole command, not a per-field list (that list rots). |
| Decide whether an origin may address a persona at all | `Persona.is_addressable_from` (`origin_allowlist` field) enforced once in `BotLogic.preprocess_message`, above both command parsing and the DP-277 control-plane gate | `single` — asks a different question from the row above (*may you reach this persona* vs *may this command reconfigure it*), which is why it is a separate gate rather than a widened `Origin.operator`. ⚠️ **Placement is the whole finding.** The first cut enforced it in `ChatSystem._orchestrate`; `discord_bot.on_message` and the portal's `dev_command` route both resolve dev commands through `preprocess_message` and **return without entering the kernel**, so the gate did nothing on the only transport it can match. ## Scheduling and deferred work

| Capability | Implementations | Verdict |
|---|---|---|
| Run work on a repeating interval | `agents/base.Agent._wait_for_next_run` (`schedule.interval` or `daily_at`, respects `_shutdown_event`) · `MemoryConsolidator.start_daemon` (`_shutdown_event` + `stop()`, drains between targets/clusters) · `mcp_client._maintenance_loop` (`MCP_RECONNECT_INTERVAL`, own wake/rate-limit logic; cancelled by its owner's `aclose()`) · `app_manager.register_task` (hosts the above; `stop=` for drainers, immediate cancel for the rest) | `by design` — decision `2026-07-30-interval-loop-shutdown-contracts` (DP-304). DP-304 fixed the real defect (consolidator had no stop condition at all, and `AppManager.shutdown()` ignored `_running_tasks`). Verified 2026-07-30. |

| Fire once at a future time | `voice/timer.TimerService` (in-memory) · Zammad `pending reminder` state via `ProposalExecutor` · `ReminderAgent` polling | `unreviewed` |
| Expire/GC stale state | `expire_stale_proposals()` (lazy sweep on read) · `ConfirmationManager.sweep_expired` (lazy sweep on read) + `rebuild_from_store` boot pass + `purge_parked_writes` retention, driven off the same sweep and throttled by `PARK_PURGE_INTERVAL` (DP-319) · `prune_agents` (fixr reaper) · LRU caps (`MAX_CONVERSATION_TAINTS`, `MAX_CACHED_API_REQUESTS`) · Hindsight 24h doc-scope gap | `unreviewed` — see [[DP-308]]. DP-319 deliberately reused the lazy-sweep-on-read idiom rather than adding a background loop (a periodic task here would re-open the DP-304 shutdown-contract problem), but had to add a **boot pass** on top: a lazy sweep only walks what is loaded, so a durable row the process never loaded is one it never expires. Any future consolidation must keep that pairing — sweep-on-read alone is not sufficient once the state outlives the process. The converse also holds and cost a review finding: a **boot pass alone is not sufficient either**, because the process durability exists for is the one that never reboots, so the retention purge had to hang off the read sweep as well. **Third pairing, same shape:** a retention purge that only deletes *terminal* rows means any row the boot pass declines to finalize — unreadable payload, or anything raising during reconciliation — is never expired and never collected. Both branches force it to `quarantined` for that reason, not merely to stop the log noise. |

## Maintaining this file

The failure mode is not that this file is wrong — it is that it goes stale and
nobody notices, exactly like the import-linter contracts did before DP-302.

- Adding a capability, a `ServiceIntegration`, a store, a loop, or a notifier →
  add or update a row **in the same commit**.
- `python scripts/arch_audit.py similar concepts` surfaces *function*-level
  regeneration mechanically. It cannot see subsystem-level parallelism — two
  subsystems on different primitives share no vocabulary, no shape and no field
  names. That is the gap this file exists to cover, and it can only be filled by
  a human or an agent reading intent.
- Every `unreviewed` row is a question, not an accusation. Resolving one means
  either consolidating, or writing the decision record that makes it `by design`.
