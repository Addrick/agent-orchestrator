## Core Data Flow

```
Interface (Discord/Gmail/Zammad)
  -> Discord bot: preprocess_message() for dev commands (sent to threads, not logged)
  -> ChatSystem.generate_response()
    -> BotLogic.preprocess_message()  -- command detection (set, what, hello, etc.)
    -> RequestBuilder.prepare_request()  -- resolve services, build history, filter tools, append user msg
      -> build_conversation_history()   -- fetch sliding window from DB
      -> retrieve_memory_block()        -- embed (sliding window + current msg), KNN search,
                                           inject <memory> block as user msg at position 0
                                           (skips memories already in sliding window via
                                            exclude_after_interaction_id; respects include_ambient)
    -> ToolLoop.run()                 -- LLM call + tool execution loop
                                         (budget: MAX_TOOL_CALLS = 15 tool calls,
                                          guard: MAX_TOOL_ITERATIONS = 25 round trips)
      -> TextEngine.stream_messages()   -- provider-specific streaming API call
      -> ToolManager.execute_tool()     -- tool execution
      -- yields TokenEvent / ToolCallStartEvent / ToolCallResultEvent / ErrorEvent
      -- + WriteParkedEvent per gated write (mid-turn, DP-297 — the loop keeps
         running, so one turn can park several and still end on ordinary text)
      -- + internal _ApiPayloadEvent (orchestrator caches), _ToolContextEvent
         (sealed tool span on the error paths), _WriteDuplicateEvent, and
         _LoopFinishedEvent (orchestrator persists the assistant turn)
    -> MemoryManager.log_message()    -- persist user + assistant messages (reply_to_id links A->Q)
    -> Response back to interface

Background (SqliteConsolidator, agent_name="memory", every 15min — registered ONLY when SEMANTIC_BACKEND=="sqlite"; Hindsight backend obsoletes it):
  Phase 1 — Embed unembedded messages (loop until exhausted per channel):
  -> get_active_channels()            -- find channels with unprocessed msgs
  -> get_unembedded_messages()        -- fetch msgs not yet in Message_Embeddings
  -> EmbeddingService.encode()        -- token-aware batch chunking
  -> INSERT INTO Message_Embeddings + vec_Message_Embeddings

  Phase 2 — Segment and summarize (loop until clear per channel):
  -> get_unsegmented_embedded_messages()  -- msgs with parent_summary_id IS NULL
  -> _segment_by_similarity()         -- centroid-based topic grouping (threshold 0.80)
                                         bridging: explicit reply_to_id link OR
                                         heuristic (lone user msg + next assistant msg)
  -> _summarize_segment()             -- LLM extracts observations via submit_memory_summary tool
  -> Store segment + summary + vec embedding in Memory_Segments / Memory_Summaries / vec_Memory_Summaries
  -> SET parent_summary_id on processed msgs

Background (MemoryConsolidator, hourly daemon via app.register_task):
  -> cluster similar episodic summaries (L1) by pairwise similarity
  -> LLM merges clusters into core profiles (L2) via submit_core_profile tool
```

## Key Components

### `src/chat_system.py` -- ChatSystem
- Orchestration kernel + public API only (post DP-200/DP-201b). Constructed by `src/bootstrap.create_chat_system` with real deps: `__init__(memory_manager, text_engine, embedding_service=None, *, personas, system_persona_names, tool_manager, models_available=None)`. Borrows `memory_manager.backend` as `self.memory_backend` and pushes the embedding service into it via `set_embedding_service` so `SqliteSemanticBackend.recall` can translate query → embedding.
- Collaborators (DP-200 slice B; DP-201b deleted the transitional private delegate seams — internal and external callers address these directly):
  - `self.request_builder` (`src/request_builder.py` — RequestBuilder): `prepare_request()`, `build_conversation_history()`, `retrieve_memory_block()`, `format_raw_history_for_llm()`, `filter_tools_for_persona()`, `format_memory_block()`, sticky taint map (`conversation_taints` / `set_conversation_taint()`), `resolve_generation_params()`, dry-run `assemble_request()`.
  - `self.turn_persistence` (`src/turn_persistence.py` — TurnPersistence): `log_user_turn()`, `commit_or_update_assistant()`, `retain_turn_safe()`, `store_api_request()` + the `last_api_requests`/`last_api_iterations` caches (DP-202 deleted the mirroring ChatSystem properties; BotLogic receives TurnPersistence as an explicit dep for dump_last/dump_history).
  - `self.confirmations` (`src/confirmations.py` — ConfirmationManager): `pending` park map keyed by **token** with a per-conversation index `_by_key` (DP-297 — keying on `(user, persona)` held at most one park, so a second write evicted the first); `park()` / `take()` / `restore()` / `list_for()`, the decision queue `enqueue()` / `drain()`, `apply()` (execute-then-patch), `patch_parked_entry()`, lazy expiry `sweep_expired()` / `expire()` / `is_expired()`, and `lock_for()` (one asyncio.Lock per conversation, serializing execute → patch → continue). The `ParkedWrite` and `Decision` dataclasses live here; `PendingConfirmation` is gone. **DP-319 — durable.** Every mutation writes through to `Parked_Writes` (own table, NOT `Proposals`: that executor's `action_type` whitelist is the privilege line, and a chat park is an arbitrary tool call). Status vocabulary `PARK_DB_*` in `memory_manager`: live = `pending` / `claimed`; terminal = `resolved` / `expired` / `interrupted` / `quarantined`. `rebuild_from_store()` runs once from `create_chat_system` and reconciles each row — restore, expire-properly, terminate a `claimed` row as `interrupted_by_restart` (**never re-executed**), or quarantine one that cannot be read or reconciled (its payload is erased and an `audit_park_quarantined` row is written). Terminal rows survive for `PARK_ROW_RETENTION` so `already_resolved()` can recognize a re-proposal of an action that already ran; a park whose row was refused keeps that guard in an in-process fallback instead. `get_parked_write_status` is tri-state (`status` / `None` / `PARK_DB_UNKNOWN`) — `restore()` fails closed on the third, or a locked store resurrects a decided write as approvable.
- `generate_response()` -> returns `Tuple[str, ResponseType, Optional[int], Optional[int]]` (collect-stream wrapper over the kernel)
- `_orchestrate()` -> shared streaming kernel — preprocess (**which is also the DP-330 origin gate**) → set TurnContext (`src/tools/turn_context.py`) → `request_builder.prepare_request` → user-log → user `retain_turn` → ToolLoop → assistant-commit → assistant `retain_turn` (taint-aware) → DoneEvent → reset TurnContext. `stream_response()` (portal) and `generate_response()` (Discord/Gmail/agents) both delegate here. Token + tool events forwarded as-is; internal `_ApiPayloadEvent` siphons into `turn_persistence.store_api_request`, `_LoopFinishedEvent` drives universal write-audit parking + assistant persistence. Both retain calls are fire-and-forget (sqlite_legacy noop; Hindsight enqueues + returns).
- **Persona origin allowlist gate (DP-330)** — enforced in **`BotLogic.preprocess_message`**, not in this kernel. First thing that function does, above command parsing: `Persona.is_addressable_from(origin)`; a persona whose `origin_allowlist` is non-empty and does not match gets `Persona '<name>' is not available from this channel.` back as an ordinary command result (the message deliberately discloses nothing about the allowlist), which every caller already renders and returns on. Three placement facts are load-bearing:
  - **(a) At the chokepoint, not in an adapter.** `preprocess_message` is the one seam every message-bearing surface passes through. The first cut put the gate in `_orchestrate` and that was **wrong**: `discord_bot.on_message` and the portal's `/api/v1/persona/{name}/dev_command` both call `preprocess_message` directly and **return before the kernel is entered**, so on the only transport the allowlist can ever match, `what prompt` / `detail` / `dump_history` — and `what origin_allowlist`, which prints the very ids the refusal withholds — all answered in full. Any future adapter that short-circuits dev commands inherits the gate for free.
  - **(b) Above command dispatch**, unlike the DP-128 quarantine gate: quarantine deliberately lets `set tools` through so the operator can repair the persona live, whereas an origin that may not address the persona must not read its config with `what prompt` either. Above *parsing* too, so a plain chat turn — which reaches no handler — is refused as well.
  - **(c) Continuation turns are exempt, structurally.** The kernel skips preprocessing entirely when resuming a resolved park, so the exemption falls out of where the gate lives rather than being a special case that can drift. Intended: the approved write has already executed by then, so refusing would suppress the summary of an action that ran. A disallowed origin cannot raise a park in the first place, so it has nothing to resolve. ⚠️ The park *token* is not itself a secret — `GET /api/v1/session/{persona}/transcript` publishes it — but resolving still requires the operator token (portal) or the owning Discord account, so the exemption does not widen approval.
  - ⚠️ **Scope: this gates addressing, not the portal's read seams.** `GET /api/v1/persona/{name}`, `/session/{p}/assemble`, `/session/{p}/transcript` and `/kobold_export` reach `request_builder` without going through `preprocess_message`, and `_setup_control_plane_auth` waves through every GET — so a restricted persona's prompt, assembled request and history remain readable by anyone who can reach the portal. Pre-existing (DP-330 neither caused nor fixed it); closing it is a portal-auth change, not an allowlist change.
- `resolve_park()` / `stream_resolve_park()` -> write-tool approval flow, keyed by a mandatory park **token** (with several writes resolvable per conversation, `(user, persona)` no longer identifies one). All write tools park for audit, not just CONFIRM mode. Sequence: `take()` the park synchronously (so a double-click cannot execute twice) → acquire the conversation lock → `drain()` every decision that arrived while waiting → `ConfirmationManager.apply()` each in approval order → ONE continuation turn over freshly-rebuilt history. The continuation opens with `_render_resolution_nudge` (a synthetic, deliberately unpersisted user turn) and carries `_ContinuationState` into `_orchestrate`; this replaced DP-124's `_ResumeState`, whose replayed *snapshot* of history could not survive a burst of independently-resolvable parks.
- Public request-assembly delegates kept on ChatSystem (portal/inspector surface): `assemble_request()`, `get_view_history()`, `get_session_memory_block()`
- `RequestContext` dataclass (in `src/request_builder.py`) bundles all pipeline state
- Re-exports for back-compat: `RequestContext`, `AssembledRequest`, the generation-event names, `_relative_time`, `MAX_CONVERSATION_TAINTS`, `MAX_CACHED_API_REQUESTS`.

### `src/bootstrap/` -- composition root (DP-200 B1)
- `load_all_personas()` (user + system personas), `build_tool_manager(memory_manager, personas)` (registers WebSearchHandler, MemoryToolHandler, MemoryRecallHandler, IngestPathHandler), `create_chat_system(memory_manager, text_engine, embedding_service=None)` — signature-mirrors the old constructor so call sites swapped 1:1. It also calls `register_credentials()` (wires the credential vault → egress scrubber; see `src/security/`) and passes `models_available=get_model_list()` into the ChatSystem constructor.
- Also where `confirmations.rebuild_from_store()` is called (DP-319) — deliberately here rather than in `main`, because a rebuild that is never called yields an empty pending set over a table of live proposals, which looks exactly like the feature working.
- Boundary rule (enforced by `tests/test_module_boundaries.py`): only the entrypoint may import `src.bootstrap`. Tests/fixtures/scripts use `create_chat_system`; pure-unit construction can call `ChatSystem(...)` directly with explicit deps.

### `src/request_builder.py` -- RequestBuilder (DP-200 B3)
- Everything between "message arrived" and "wire payload": `build_conversation_history` (per memory mode, via `fetch_raw_history` dispatch), `format_raw_history_for_llm` (incl. tool_context replay + group-chat name prefixes; **DP-296 ordering guard** — a replayed tool block is dropped unless the preceding entry is a `user` turn, because the history limit can leave a tool-bearing assistant row oldest and Gemini rejects a wire array that opens with a function call: *"function call turn must come immediately after a user turn or after a function response turn"*), `retrieve_memory_block` (backend `recall` → `<memory>` block; `MEMORY_RETRIEVAL_ENABLED`/`MEMORY_MAX_SUMMARIES_IN_CONTEXT`; `exclude_after:N` recency tag), `filter_tools_for_persona` (policy + bindings + model compat), `resolve_generation_params`, `prepare_request` (history + LTM injection + client_messages fallback + token budget via `truncate_messages_to_budget`, then `drop_orphaned_tool_head`), `assemble_request` (S5 `/assemble` dry-run — parity with live by construction), `get_view_history` / `get_session_memory_block` (DP-130/136 public seams), module-level `build_scope_tags`.
- Owns the sticky per-conversation taint map (`conversation_taints`, LRU-bounded by `MAX_CONVERSATION_TAINTS`); read during prepare, written back by the kernel post-loop.
- Persona access via `persona_lookup` closure (NOT a dict reference) so post-init `chat_system.personas` rebinds stay visible.

### `src/confirmations.py` -- ConfirmationManager + ParkedWrite (DP-200 B2, rewritten DP-297 / DP-319)
- Orchestrator-owned store for gated writes, keyed by **`token`** with a per-conversation index `_by_key[(user, persona)]`. DP-297 replaced the old 1:1 `(user, persona)` key (where a second park evicted the first, emitting `audit_parked_evicted`); one turn can now queue N proposals, each resolvable independently and out of order. ToolLoop stays stateless across the park. `PendingConfirmation` is gone — `ParkedWrite` and `Decision` are the dataclasses here.
- `ParkedWrite` is ONE call, deliberately carrying **no conversation snapshot** — the continuation rebuilds live history from the DB. That is what makes out-of-order resolution safe: every snapshot would predate its siblings, so replaying one forks the conversation.
- **Durable since DP-319**: the `Parked_Writes` table (SQLite). In-memory dicts stay the live index (`take` must remain a pure sync pop to keep its atomicity, and `asyncio.Lock`s cannot be persisted), the DB is **written through** on every mutation, and read back once at boot.
  - Row states (`PARK_DB_*` in `memory_manager`): `pending → claimed → resolved | expired | interrupted | quarantined`. `take()` pops in memory AND `claim_parked_write`s the row; `restore()` releases it. `quarantined` is its own terminal state, not a flavour of `interrupted` — an interrupted park may have executed, a quarantined one provably did not, and `resolution` is the column a forensic query filters on. This vocabulary is deliberately **not** the same as `tool_loop`'s `PARK_STATUS_*` (which is what the *model* reads in replayed history); they overlap by accident on `"expired"` and diverge on purpose, so the near-homonyms must not be used interchangeably.
  - `restore()` is tri-state. `release_parked_write` returning False is ambiguous, so it consults `get_parked_write_status`, which answers `status` / `None` (no such row) / `PARK_DB_UNKNOWN` (the store could not tell). **Fails closed on the third** — a transient `database is locked` read as "no row" re-INSERTs `status='pending'` over a decided row and resurrects an executed irreversible write as approvable.
  - A park whose INSERT was refused (`insert_parked_write` serializes `write_call` strictly, so a `datetime` argument hashes fine but will not store) stays live in memory with `persisted=False`. `apply()` then records its outcome in an in-process fallback map, because the DB-backed re-execution guard cannot see a row that does not exist.
  - `finalize_parked_write` keeps the row (the re-execution guard reads it) but NULLs `write_call` / `audit_info` / `confirmation_text` — a decided park retains only a **hashed** `call_identity` plus its outcome. `purge_parked_writes` drops terminal rows past `PARK_ROW_RETENTION`.
  - `rebuild_from_store()` runs from the composition root (`src/bootstrap`), not from `main`. Three populations: in-TTL `pending` reinstated; past-TTL `pending` properly expired (patch + audit — the lazy sweep only walks what is loaded, so a row it never loaded is one it never expires); `claimed` terminated as `interrupted_by_restart` and **never re-executed**, because the write may already have run. A fourth outcome, `quarantined`, covers a row that cannot be *read* (undecodable `write_call`) or cannot be *reconciled* (anything raising out of the per-row work): forced terminal, payload erased, `audit_park_quarantined` logged. Both branches must quarantine — returning instead leaves the row `pending` forever, since `purge_parked_writes` only deletes terminal rows, so it fails identically on every later boot while its unscrubbed arguments stay on disk.
  - `rebuild_from_store` also marks `_last_purge`; the retention purge otherwise ran twice, once at boot and again on the first `park()`/`list_for()`.
  - Deliberately NOT the `Proposals` table: `ProposalExecutor`'s `action_type` whitelist IS the ADR-2026-07-04 privilege separation, and a chat park is an arbitrary tool call.
- Surface recovery after a restart: the portal is free (`list_for` on every transcript load); Discord's `_confirm_registry` (message id → token) and `_rendered_park_tokens` both die with the process, so old buttons go dead and `_post_pending_proposals` re-posts on the next message in that channel. A click on a dead button is answered (`_notify_stale_button`) rather than dropped — gated on the bot's OWN ✅/❌ still being on the message, which is what distinguishes a proposal from an ordinary answer someone reacted to. ⚠️ **the handler must be `on_raw_reaction_add`**: discord.py dispatches the cooked `on_reaction_add` only for messages still in its `max_messages` (1000) client cache, which is empty after a restart — i.e. it cannot fire in the exact case this exists for, and it also stops resolving live parks whose message ages out.
- Lifecycle surface (the seam): `park` / `take` / `restore` / `list_for` / `lock_for` / `enqueue` / `drain` / `apply` / `patch_parked_entry` / `sweep_expired` / `expire` / `is_expired` / `note_duplicate_ref` / `already_resolved` / `rebuild_from_store`.
- `apply()` executes (or refuses) then patches the history entry **in place** — ordering matters, or the continuation reads its own proposal as still pending. `Decision.status` separates the two axes (`approved` = operator verdict, `ok` = did the tool run) so approved-but-failed is not recorded as success. `DENIAL_INSTRUCTION` / `INTERRUPTED_INSTRUCTION` live in the patched entry, not in an ephemeral nudge, so the verdict and what to do about it share one lifetime.
- Re-execution guard (DP-319): `already_resolved` answers "did this exact call already RUN?" via `find_resolved_parked_write`, scoped to `PARK_STATUS_APPROVED` inside `PARK_REEXECUTION_GUARD_WINDOW` (15 min). Injected into ToolLoop as `resolved_lookup`, beside `pending_lookup`. Needed because `pending_lookup` is structurally blind during a continuation (the park was already taken) — which is exactly when the model re-proposes. **Continuation turns only**, and that scoping is the correctness argument: left running on ordinary turns it would answer a legitimate "restart that service again" with "that already happened", silently, for fifteen minutes. The identity it keys on is `tool_loop.write_call_identity_hash` (name + canonicalized args, sha256) — deliberately beside `write_call_identity` rather than on `MemoryManager`, since drift between the canonicalizer and the digest fails OPEN as a silently disabled guard.
- Uses a `tool_manager_lookup` **closure**, not a bound reference, so a post-init `chat_system.tool_manager` swap is visible here (ToolLoop reads per-call).

### `src/turn_persistence.py` -- TurnPersistence (DP-200 B4)
- Turn write-paths: `log_user_turn` (fresh user row, or `handle_portal_retry` archival on retry; empty-message phantom-row guard), `commit_or_update_assistant` (UPDATE on retry / INSERT otherwise; returns canonical assistant id), `retain_turn_safe` (fire-and-forget `memory_backend.retain_turn` with scope tags + untrusted bit).
- Owns `last_api_requests` / `last_api_iterations` (dump_history's data; LRU-bounded by `MAX_CACHED_API_REQUESTS`) via `store_api_request`. ChatSystem exposes both as read/write properties; BotLogic receives TurnPersistence as an explicit dep (DP-202).
- One of the egress seams where the `SecretScrubber` is enforced (API-payload caching).

### `src/generation_events.py` -- streaming event dataclasses
- Lives outside chat_system to break a circular import (chat_system ↔ tool_loop). chat_system re-exports the names so `from src.chat_system import TokenEvent, DoneEvent, ResponseType` still works.
- `TokenEvent(delta)` -- incremental text chunk
- `DoneEvent(text, response_type, assistant_id, user_interaction_id)` -- terminal success
- `ErrorEvent(message)` -- terminal failure
- `ToolCallStartEvent(tool_name, arguments, call_id)` -- tool invocation surfaced mid-stream (tool revamp v1)
- `ToolCallResultEvent(call_id, tool_name, result, error)` -- paired result; `error` populated on tool failure
- `PendingConfirmationEvent(text, write_calls, persona_name, token, audit_info=None)` -- one gated write surfaced mid-stream as its own approve/deny affordance. ⚠️ Do not confuse it with `tool_loop.WriteParkedEvent(token, write_call, audit_info, confirmation_text, turn_tainted)`, which is the *loop*-level event: ToolLoop emits a `WriteParkedEvent`, and `_orchestrate` translates each one into a public `PendingConfirmationEvent` (with `write_calls=[ev.write_call]`) for interfaces. `WriteParkedEvent` is public-named but lives in `tool_loop`, not here.
- `GenerationEvent` Union; `ResponseType` enum: DEV_COMMAND, LLM_GENERATION, PENDING_CONFIRMATION. **The `PENDING_CONFIRMATION` *enum member* is vestigial as of DP-297** — nothing sets it as a turn's response type any more (a turn that parks writes still ends with real text and persists as LLM_GENERATION). It survives only so old rows and the retry branch in `turn_persistence` keep their meaning. The *event class* `PendingConfirmationEvent` is very much alive and is still yielded per parked write.
- `last_api_requests` dict caches payloads for dump_last/dump_history (keyed by user+persona)

### `src/tools/tool_loop.py` -- ToolLoop
- Stream-shaped tool loop extracted from `_orchestrate` (tool revamp v1, supersedes the old `plans/toolloop_extraction.md`).
- `ToolLoop(text_engine, tool_manager, max_iterations=MAX_TOOL_ITERATIONS, max_tool_calls=MAX_TOOL_CALLS)` — constructed per-call by `_orchestrate` so tests that swap `chat_system.text_engine` post-init still take effect. **DP-335 split the two limits**: `max_tool_calls` is the turn's budget (counted in calls executed, so it means the same thing on a batching and a one-call-per-message model), `max_iterations` is the pure runaway guard on provider round trips.
- `run(persona, conversation_history, params, tools, ...)` — async generator. Drives `text_engine.stream_messages` per iteration, forwards `TokenEvent`s, surfaces tool calls as `ToolCallStartEvent` / `ToolCallResultEvent`, mutates `conversation_history` in place (orchestrator + resume path read it back).
- **The assistant history entry keeps its prose (DP-338).** Each tool-calling iteration appends `{"role": "assistant", "tool_calls": [...]}` **plus a `content` key** holding whatever the model wrote beside its calls (key omitted entirely when there is none, so a call-only iteration keeps the old two-key shape). That prose is the plan for the batch; without it the next iteration re-read a transcript in which the calls had no stated reason, re-derived the plan from an identical history, and re-emitted the same batch. Providers park the prose in two places, so the loop reads both: the streaming ones delta it out and zero `full_text` on a tool turn, while agy's one-shot route emits no deltas at all and carries it on `done`. The same value feeds `audit_info.model_reasoning` — reading the deltas alone meant every agy-backed persona parked its writes with a blank "why" on the operator's dialog. The prose is run through the **egress scrubber before it enters history** (DP-225 boundary 2): it is sealed into `tool_context`, persisted to `User_Interactions` and replayed to the provider next turn, so it is a persistence path in its own right — scrubbing only `audit_info` below it would show the operator a redacted sentence while storing the unredacted copy. The Google history builder emits it as a leading `Part(text=...)` in front of the `function_call` parts, or the route would store the plan and strip it again on the way to the wire.
- Implements **universal write-audit**: on any iteration where a batch contains a `WRITE_TOOLS` call, the loop runs the read calls, then emits one `WriteParkedEvent` **per write call** (each with its own token + `audit_info` block: per-action `irreversible` / `always_confirm` / `service_binding` / `sensitivity` / `enrichment`, plus turn `tainted` / `taint_sources` / `model_reasoning`). This is unconditional — execution mode is recorded in `audit_info` for display only, never gates parking. Taint (`turn_tainted` from `produces_untrusted` read tools) and irreversibility flags are computed here for the audit surface.
- **DP-297: parking is no longer a terminal exit.** The loop answers each gated call inline with a synthetic `awaiting_human_approval` tool result and *falls through to the next iteration*, so the model keeps working — and may propose again — while the operator decides. A turn can therefore park several writes and still end on ordinary text. `write_call_identity` (name + canonicalized arguments, id excluded) backs a duplicate guard so a model ignoring the "do not re-submit" instruction cannot turn N iterations into N copies of one affordance; the suppressed call gets a `duplicate_of_pending` result and is patched when the original resolves.
- Tool errors (returned as `{"error": ...}` by `tool_manager.execute_tool`) surface via `ToolCallResultEvent.error`; the loop continues so the model can adapt instead of hard-stopping.
- Internal events `_ApiPayloadEvent` / `_LoopFinishedEvent` / `_ToolContextEvent` / `_WriteDuplicateEvent` are loop-private — they let the orchestrator handle api-payload caching, write-audit parking, duplicate-entry patching, and assistant-row persistence without leaking into the public event surface. `WriteParkedEvent` is the one non-underscore loop event, because interfaces consume it.
- **Iteration-cap text (DP-335).** `render_max_iteration_text(history, start, max_iterations)` renders the DEV_COMMAND reply for the `max_iterations` exit from the same history slice sealing uses: one numbered line per tool call with arguments (scrubbed), outcome, and a `(same call as #N)` marker for verbatim repeats. Replaces the canned "stuck in a loop" sentence, which named no tool and read as a fault even when every call had returned `ok`. Full rationale: `docs/tool_loop_exits.md`.
- **Tool-context sealing (DP-296).** `seal_tool_context(history, start, reason)` serializes this turn's tool messages and synthesizes a `{"status": "not_executed", "reason": ...}` result for every `tool_call` left unanswered (`awaiting_approval` / `error` / `max_iterations_exceeded`). It does not mutate `conversation_history` — the continuation path still needs the unsealed list so real results can land. Every exit persists through it: the clean finish, the park, both error paths, and the iteration cap. Before this, only the clean finish persisted, so a gated or errored turn lost every tool call it made and the model saw nothing but its own prose on the next turn. Sealing exists because an unpaired `tool_call` block is *unsendable* — both Anthropic and Gemini reject it, which is why these exits used to store `None` rather than the raw slice.
- The error paths have no `_LoopFinishedEvent` to carry the context, so they emit `_ToolContextEvent` first; `_orchestrate` siphons it exactly like `_ApiPayloadEvent` and commits an assistant row before returning on `ErrorEvent`.
- Park-status vocabulary the *model* reads in replayed history (`PARK_STATUS_*`, defined here, distinct from `memory_manager`'s `PARK_DB_*` row states): `awaiting_human_approval`, `approved`, `denied`, `approved_but_failed`, `expired`, `interrupted_by_restart`, `quarantined_unreadable`, `already_resolved`, `duplicate_of_pending`.

- **`agy` route (DP-127, model prefix `agy-*`):** drives the local `agy` CLI via subprocess on the OAuth tier (Gemini 3.5 Flash), not an API key. `_render_agy_prompt` flattens the full history into one role-tagged transcript (stateless, re-flattened each tool-loop turn); `_render_agy_tool_protocol` injects tool descriptions + asks the model to emit one or more `<tool_call>{json}</tool_call>` blocks; `_parse_agy_tool_call` parses **every** well-formed block back into the standard `{"id","name","arguments"}` shape so DERPR's own tool loop executes them (engine keeps full policy/CONFIRM/taint control — agy never runs tools itself), and the prose beside the blocks rides back on the result's `content` for the tool loop's history entry. **DP-338:** this used to be a first-match `re.search`. Blocks 2..N were dropped with no execution, result, error or log line, so a model told to batch its independent reads (which hypr's prompt explicitly asks for) saw one of N requests answered and re-emitted the same batch — and since block 1 never changes, that is a fixed point which spins until the turn's call budget trips. Observed in prod as 15 identical `pve_status` calls over 15 iterations. A malformed block among well-formed ones is now skipped rather than failing the response (and **logged** — `strip_tool_call_blocks` removes it from the prose too, so without a log line the dropped call is invisible in `calls`, in `content`, in the transcript and in the logs at once); a response whose blocks are **all** malformed still returns `None`, because that is the signal the empty-response retry keys off. The **field policy matches `_ToolCallStreamParser._commit_call`** as well as the extraction: `name` is required, `arguments` defaults to `{}` (a no-arg tool's block is legal), a stringified args object is JSON-decoded and a non-object is coerced to `{}` — handing a `str` to `execute_tool(name, **args)` raises TypeError inside the loop, which spends a budget slot to return "Tool execution failed". The streaming parser (`_ToolCallStreamParser.finalize`) always returned every block, so local models were never affected — agy's one-shot path was the only first-only parser. `_run_agy_cli` spawns with `stdin=DEVNULL` (or it blocks on an interactive permission prompt), **no** `--dangerously-skip-permissions`/`--add-dir` (so agy's own tools stay gated and it can never run them — DERPR drives every tool itself), in a throwaway tempdir, killing the process tree on cleanup. **Platform-agnostic since DP-324:** the route used to be POSIX-only (`_ensure_agy_supported()` refused native Windows, where older agy builds wrote their response only to a TTY while the engine captures piped stdout, so the response was always empty). agy >= 1.1.9 writes to a pipe on Windows, so the guard and its engine seam are gone and `AgyProvider.ensure_supported` is the base class no-op. The platform split now lives entirely in `_subprocess.py`: `_spawn_isolation_kwargs()` (POSIX `start_new_session` via setsid vs Windows `CREATE_NEW_PROCESS_GROUP` — `start_new_session` is silently ignored on Windows, so passing it there would look like isolation while providing none) and `_adopt_process_tree()` / `_kill_process_tree()`. **`CREATE_NEW_PROCESS_GROUP` buys only Ctrl-C isolation, not teardown** — `taskkill /T` walks parent-pid links from a snapshot and reaches the same descendants with or without the flag (verified), so it is not what makes cleanup work. Teardown: POSIX `killpg` unconditionally, including after a clean exit, because these CLIs leave background helpers behind; Windows gets the equivalent from a **job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`** (`_adopt_process_tree` assigns the child right after spawn; closing the handle in the `finally` kills whatever is still inside, live parent or not — and the kernel closes it for us if derpr dies). `taskkill /F /T` is only the fallback when the job assignment failed, is skipped once the process has exited (the walk needs a live parent pid), and is spawned **without waiting** — blocking in that `finally` would stall the one event loop serving Discord, the portal and every other provider. `cc` remains POSIX-only while `CC_SANDBOX` is on — that guard is about Claude Code's OS sandbox, not about stdout. Text-only (no images). **Prompt is argv-bounded (DP-299):** the whole prompt is one argv entry (`agy --print <prompt>`; the CLI has no stdin/prompt-file transport) and `execve` caps a single argument at `MAX_ARG_STRLEN` = 128 KiB, while the engine bounds history by *tokens* (~131k ≈ 0.5 MB) — so `providers/_subprocess.fit_cli_prompt` clamps the prompt to `cli_prompt_budget()` (96 KiB on POSIX; 20 KiB on Windows, where `CreateProcess` caps the *whole* command line at `MAX_COMMAND_LINE_CHARS` = 32767 chars — a shared pool across every argv entry, so the cc route's `--system-prompt` gets its own smaller `cli_arg_budget()`. Budgets are resolved per call, not frozen at import, so both platforms stay testable from either host). **The budget's unit is `_cmdline_cost`, not bytes:** Windows has no argv vector — Python renders one string with `subprocess.list2cmdline`, which quotes entries containing whitespace and escapes every embedded `"` as `\"`, so the OS measures the *escaped* form. Measured expansion: x1.00 plain ASCII, x1.14 a JSON tool-result transcript, x2.00 quote-dense. Budgeting raw bytes against that cap is how a prompt the trimmer believed fit still died at the spawn with WinError 206, so `_cmdline_cost` costs the escaped string and `_keep_head_within` binary-searches the cut point (no arithmetic maps a budget to an offset once cost ≠ length), keeping the preamble (system prompt + tool protocol) whole and eliding the oldest history **messages**. Elision is message-granular because it consumes `render_transcript_blocks` (one `TranscriptBlock` per message, `role` retained) rather than re-splitting the flat transcript on blank lines — message content can itself contain blank lines, so re-splitting yields fragments and cuts mid-message. When nothing fits, the newest *user* block wins over a newer tool result (in the tool loop the last block is the tool output; keeping it while dropping the question leaves the model a blob and no task), and truncation keeps the block's **head** so the `User:`/`Tool(name):` label survives. Without any of this the spawn failed with `OSError [Errno 7] Argument list too long`. `exec_cli` wraps spawn `OSError` into `LLMCommunicationError`, quoting the payload size **only** for the oversized-command-line failure (`errno.E2BIG` on POSIX; WinError 206 on Windows, which Python raises as a `FileNotFoundError` — matching on errno alone would report it as a missing binary) — `FileNotFoundError`/`PermissionError` are `OSError` subclasses and must not be reported as size problems. The same clamp guards the `cc` route, whose `--system-prompt` is a second argv entry bounded separately by `clamp_cli_arg`. The Antigravity *SDK* route was rejected (API-key-only, Model-A-native) — see `project/decisions/2026-05-29-agy-sdk-oauth-finding.md`.
- **`cc` route (DP-222, model prefix `cc-*`):** drives the local `claude` CLI via subprocess (one-shot; the `CcProvider` in `providers/cc.py` with a dedicated `_cc_limiter`, resolved ahead of the `"claude" in model_name` branch). `_cc_model_arg` maps `cc-sonnet`→`sonnet` (bare `cc-` falls back to `sonnet`). POSIX-only when sandbox is on (`_ensure_cc_supported`, gated by `CC_SANDBOX`). Structural parity with `agy` (subprocess-per-call, persistent per-persona/global workspace, dedicated rate limiter) but a deliberate divergence: cc **ignores** the engine's `tools` argument and lets Claude Code run its OWN sandboxed tools under `--dangerously-skip-permissions` bounded by the OS sandbox (Seatbelt/bubblewrap via `_build_cc_sandbox_settings`), returning final text — DERPR's tool loop does not wrap it. `_resolve_cc_workspace` precedence: per-call `cc_workspace_override` (used by DP-227 fixr to point at an agent's worktree) > `CC_WORKSPACE_DIR` > per-persona dir > global dir; `_cc_workspace_locks` serialize same-workspace runs. Config: `CC_SANDBOX`, `CC_ALLOWED_TOOLS`, `CC_MAX_TURNS`, `CC_WORKSPACE_*`, `RATE_LIMIT_CC_RPM`. **DP-314:** before argv is built (order is load-bearing — the sandbox `allowWrite` entry is derived from whether the notes clone exists), `utils/notes_workspace.prepare_workspace_notes` seeds `CLAUDE.md` into non-checkout workspaces and links the ONE shared notes clone in as `memory/`. ### `src/origin.py` -- typed message origin (DP-277)
- Leaf value object (zero `src.*` imports, like `tool_policy`), so any layer can carry an `Origin` without a cycle. `Origin(transport, server_id, channel_id, author_id, operator)` plus the `ANONYMOUS` secure default every caller that asserts no authenticated origin falls back to.
- `operator` is set by the interface adapter from **transport-authenticated facts only**, never from caller-supplied request fields: Discord matches gateway-asserted ids against `OPERATOR_ALLOWLIST`; the portal uses a validated `DERPR_CONTROL_TOKEN`; ticket bodies / Gmail / unauthenticated portal calls are structurally `operator=False`.
- `parse_operator_allowlist(raw)` → `(server, channel, author)` tuples from `server_id[/channel_id[/author_id]]` entries; missing or `*` components match anything at that level, and **malformed entries are dropped with a warning** (a wildcard server is refused outright — it would grant every guild the bot is in). Fail closed: a typo narrows access, never widens it.
- `is_discord_operator(...)` matches those tuples; a missing `server_id` never matches, so DMs are out by construction.
- `is_origin_allowed(allowlist, origin)` (DP-330) wraps the matcher for the *persona* allowlist: empty allowlist = unrestricted, non-Discord transport = refused. The transport check is belt-and-braces — the portal receives a **caller-supplied** `server_id` in its request body, and an adapter that ever copied it into an `Origin` must not thereby widen a persona allowlist.
- Two gates consume this, asking different questions, and **both live in `BotLogic.preprocess_message`** — the addressing gate first (may this origin *address this persona* at all — `Persona.is_addressable_from`, DP-330), then the control-plane gate (may this *command* reconfigure things — `Origin.operator`, DP-277). Same function because it is the only seam all three message-bearing surfaces share; see the kernel section for why the addressing gate could not stay in `_orchestrate`.

### `src/persona.py` -- Persona
- Stateful LLM config: model, system prompt, token limit, temperature, top_p, top_k
- True domain leaf since DP-204: zero `src.tools` imports. Holds a `ToolPolicy` (the `src/tool_policy.py` leaf, like `generation_params`) and the DP-128 quarantine STATE only (`security_block_reasons`, `is_security_blocked()`, `set_security_block_reasons()` pure mutator); the validation that produces the reasons lives in `src/tools/composition.py`

- `MemoryMode`: CHANNEL_ISOLATED, SERVER_WIDE, PERSONAL, GLOBAL, TICKET_ISOLATED
- `get_history_messages()` -> supports dynamic override via hello/goodbye commands (increments by 2 per turn)
- Service bindings list determines which tools and services are available
- `origin_allowlist: List[str]` (DP-330) — which origins may address this persona at all, in the `OPERATOR_ALLOWLIST` entry form `server_id[/channel_id[/author_id]]`. **Empty = unrestricted**, so every pre-DP-330 persona file is unchanged by construction. Matched by `Persona.is_addressable_from` → `origin.is_origin_allowed`. Persona imports `src/origin.py`, which is a leaf like `tool_policy`/`generation_params`, so the domain-leaf rule still holds. Privileged like `explicit_overrides`: CLI-settable via the operator-gated `set origin_allowlist` (**audited** — `origin_allowlist_change`, same edit boundary as `explicit_overrides_change`), and **deliberately not PATCH-able**.
  - `Persona._normalize_origin_allowlist` runs on **both** write paths (construction and `set_origin_allowlist`), so the field reads back identically however it was last written. It exists because the value comes from a hand-edited JSON file and cannot be trusted to match its declared `List[str]`: **ints are accepted** (a guild id is a number, and the raw value used to hit `','.join` and raise `TypeError`, which `load_personas_from_file`'s blanket `except` swallowed into a `None` return — dropping *every* user persona and letting the next mutating dev command save an empty list over the file); a **bare string is one entry**, not one per character; and entries are **parsed one at a time**, because joining them with `','` first let a comma *inside* an entry grant a guild nobody authored — a typo that widens.
    - **The entry grammar has one owner: `origin.parse_operator_allowlist_entry`**, with `origin.split_allowlist_entries` owning the separator. Both were re-derived at their call sites — the tokenizer was copy-pasted into `persona_fields._parse_string_list_arg` and the normalizer, and "the parser did not split this" was inferred as `len(parse_operator_allowlist(text)) == 1 and ',' not in text`. That proxy is the widening rule (*a comma is the separator, so an entry containing one is two grants glued together*) written somewhere it cannot be maintained: adding a separator in `origin.py` would silently convert those rejections into grants. `parse_operator_allowlist` is now a loop over the single-entry parser, so the env-var path and the persona path cannot disagree.
    - **A no-op `set` is not a mutation.** `set_origin_allowlist` returns early when the normalized result matches what is already loaded, so `mutated` — which drives both the audit row and a full `personas.json` rewrite — means "the field changed". `set origin_allowlist none` on a persona that never carried the key used to report True, writing an audit row with identical prior/new state and flipping `declared` forever, so `to_dict` began emitting `"origin_allowlist": []` for a persona whose policy had not changed.
  - **Fail closed on a wholly-malformed list.** Empty means unrestricted, so letting a typo'd list parse down to empty converted a restriction into a wide-open persona while `what origin_allowlist` still reported the authored entries. Instead the persona carries an unmatchable sentinel and is unreachable. Three things had to be true at once for that guarantee to actually hold, and the first cut got each of them wrong:
    - **The trigger is "something was supplied", not "something survived stringification"** — `if (authored or rejected) and not parsed`. Keying it off `authored` alone skipped the two shapes that never reach that list (`[None]`/`[True]`/`[["x"]]`, and blank-only `["", " "]`, which was `continue`d rather than rejected), so the branch never fired and the persona came out **unrestricted** on input already diagnosed as bad.
    - **Persistence must round-trip the fail-closed state**, so `store.to_dict` writes `get_origin_allowlist_for_persist()` — the *raw* authored value when unreachable. Writing the normalized list dropped the unstringifiable entries, saving `[null]` as `[]`; unreachable in memory, unrestricted after the next restart, and one `set temp 0.8` was enough to trigger the rewrite.
    - **Reporting must distinguish unreachable from unrestricted.** `origin_allowlist_is_malformed()` is also True when *some* entries parsed, so it cannot carry this alone; `origin_allowlist_is_unreachable()` (the sentinel is present) is what `what origin_allowlist` and the setter's reply branch on first. Both fail-closed shapes leave the normalized list empty and were being reported as "unrestricted (any origin may address it)" — the opposite of the truth.
  - **Lockout is real and one-way; the docs claimed otherwise.** `set origin_allowlist` targets the *addressed* persona and has no cross-persona form, so "run it while addressing a different one" — which `user_guide.md`, this file, the setter docstring and a test docstring all said — clears the **other** persona's restriction while the locked-out one stays locked. Compounding it, `is_origin_allowed` refuses every non-Discord transport once the list is non-empty, so setting one over the portal locks the portal's own `dev_command` route out on the next call. Real recovery: a Discord origin the list admits, or editing `data/personas.json` and restarting.
  - `origin_allowlist_is_declared()` distinguishes "never had the key" from "explicitly `[]`". `store.to_dict` keys off it so a persona shipped with `"origin_allowlist": []` — the operator's only in-file hint that the knob exists — is not erased by the first mutating dev command, while a persona that never carried the key still round-trips unchanged.
- `include_ambient_memory: bool = True` — whether to include ambient-channel memories in retrieval; controlled by `get_include_ambient_memory()`

### `src/memory/context_budget.py` -- Context budget enforcement (Phase 3)
Pure helpers for enforcing per-persona `max_context_tokens`. **One callsite today: `request_builder.prepare_request`**, which calls `truncate_messages_to_budget` and then `drop_orphaned_tool_head`. (Both docs used to claim a second callsite in `kobold_engine_adapter` `/chat/completions`; that went away when Phase D moved budget enforcement engine-side — the adapter's OAI route is now a pure transcoder and the native passthrough routes prune nothing.) Future home for dynamic LTM-depth modulation, retrieval-score-weighted budget allocation, and a real tokenizer swap.
- `estimate_tokens(text)` -> `(len(text)+3)//4`. No tokenizer roundtrip.
- `truncate_messages_to_budget(messages, max_tokens)` -> `(pruned, dropped_count)`. Drops oldest non-system messages until total ≤ budget. Preserves all `role=='system'` messages and the most recent `role=='user'` message (so the current turn is never evicted). No-op when `max_tokens` is None / non-positive / already under budget.
- `drop_orphaned_tool_head(messages, injected=None)` -> `(repaired, dropped_count)` (DP-298). A history that *starts* on an `assistant`-with-`tool_calls` or a `tool` message whose triggering user turn is gone is rejected by Google (400 *"function call turn must come immediately after a user turn"* for a leading call; *"function response turn must come immediately after a function call turn"* for a leading bare result). **Backstop, not primary defense, for the DB path:** DP-296 made `truncate_messages_to_budget` treat an `assistant`+`tool_calls` message and its `tool` answers as one atomic span, and gave `build_conversation_history` a guard that refuses to replay `tool_context` unless a `user`/`tool` turn precedes it. The path where this is still load-bearing is **`client_messages`** (kobold-lite supplies its own array, taken verbatim apart from stripping one leading system message) — neither DP-296 guard runs there. The scan walks **through** a leading run of non-conversational preamble before looking for the orphan: `role=='system'` entries plus anything in `injected`, matched by **identity**. `prepare_request` passes the LTM recall block as `injected` — it is inserted at index 0 as a `user` message but is not a real conversational turn, and without the skip it shielded the orphan behind it. Identity matching means a caller can pass a block the pruner may or may not have dropped and get the right answer either way. Called once, last thing in `prepare_request`, after both truncations.
- Budget semantic is **kobold-style total ctx** (prompt + reserved response). Effective prompt prune budget = `persona.max_context_tokens - persona.response_token_limit`.

### `src/agents/` -- Agent Framework

**`base.py` -- Agent (ABC)**
Abstract base for autonomous background workers. Not user-interactive — poll external systems on a schedule and act independently.
- Lifecycle: `start()` → `_on_start()` → `[loop: deploy() every interval]` → `stop()`
- `deploy()`: Abstract — subclass implements one work cycle
- `_build_llm_context()`: Minimal context (user prompt + optional action history injection)
- `_get_action_history_message()`: Injects recent actions into LLM context if `action_history_limit > 0`
- Auto-loads system personas from file on init (agents invoke system personas for read-only analysis)
- Config: `schedule` (dict, e.g. `{"interval": 30}`), `action_history_limit` (int), `agent_name` (str)

Trajectory-logging contract (DP-116a) — root + children written to `Agent_Actions`:
- `_log_task_root(action_type, trigger_context, action_payload, contexts, outcome="pending")`: opens a root row, JSON-serialises + ASCII-safe-truncates `action_payload`, attaches `Agent_Action_Contexts` rows; returns the root `action_id`.
- `_log_step(parent_id, action_type, action_payload, outcome, outcome_payload, contexts)`: child row under a root.
- `_add_contexts(action_id, [(type, value), ...])`: idempotent context-tag insert (drops null/empty).
- `_finalize_action(action_id, outcome, outcome_payload)`: terminal update on a root.
- `_serialize_payload(data)` / `_truncate_ascii(text, max_len=None)`: dict→JSON, ASCII-only (`encode("ascii","replace")`), capped at `MAX_PAYLOAD_CHARS` (4000) unless `max_len` overrides. ASCII-only is defensive against Hindsight's utf-8→latin-1 mangling on some endpoints.

Hindsight bridging (DP-116b) — fire-and-forget bridge of a finalized series into Hindsight:
- `_format_action_series_prose(parent, steps, contexts)`: flattens a root + children + context tags into dense k:v prose (no JSON braces, no nulls). Capped at **16000** chars (Hindsight chunks at 10k internally — a belt on pathological loops, never expected to fire when log-time ref discipline holds).
- `_retain_action_series(action_id)`: called by subclasses after `_finalize_action` on a root. Re-reads the series from `Agent_Actions` (idempotent across restarts), formats prose, enqueues a `retain_experience` POST with stable `document_id=f"agent_action:{action_id}"` (`_action_document_id`, prefix `AGENT_HISTORY_DOC_PREFIX`) + `content_override=<prose>`. Fire-and-forget through `HindsightBackend`'s queue; SQLite-shape backends raise `NotImplementedError`, which is swallowed — bridging is Hindsight-only and opportunistic.
- Class attrs `experience_bank` / `experience_persona` select the destination bank (default: `agent_name`). DispatchAgent points both at `DISPATCH_PERSONA_NAME` so dispatch series mingle into the `dispatch_analyst` persona bank; ReminderAgent + SqliteConsolidator default to their `agent_name`.

**`agent_manager.py` -- AgentManager**
Central registry and lifecycle controller.
- `register(name, AgentClass, default_config)`: Register agent blueprint
- `start_agent() / stop_agent() / restart_agent()`: Lifecycle control (creates asyncio tasks)
- `auto_start()`: Starts agents where config has `auto_start: true`
- Convention-based DI (`_di_kwargs`): inspects agent `__init__` signature, injects `chat_system`, optionally `zammad_client`, `notification_router`, `agent_config`, plus **any registered single-shot inference agent whose name matches a param** (DP-294 — e.g. `ZammadBot(content_classifier=…)`; the injected instance is `get_inference_agent`'s cached singleton). Shared by scheduled (`_build_agent_instance`) and inference (`get_inference_agent`) paths.
- `register_inference_agent(name, cls)` / `get_inference_agent(name)`: single-shot inference agents (DP-292) — DI-built on first lookup, cached, never launched as a task. `content_classifier` + `date_tagger` register here.
- Config merging: agents.json < registration defaults < runtime overrides
- `notification_router`: Lazy-set after construction

**`dispatch_agent.py` -- DispatchAgent**
Routes triaged tickets to notifications. Pipeline per ticket:
1. Fetch ticket + triage note from Zammad
2. LLM call to `dispatch_analyst` persona → priority, summary, reasoning (JSON)
3. Route notification via `NotificationRouter` (channel/recipient from agents.json config, not LLM-chosen)
4. Tag ticket as dispatched in Zammad
5. Log action outcome

Trajectory logging (DP-116a): each `_dispatch_ticket()` call writes one `dispatch` root row plus child rows for `tool:zammad.get_ticket`, `tool:zammad.get_ticket_articles`, `llm_step` (dispatch_analyst), `tool:notification.send`, `tool:zammad.add_tag`. **`reminder_agent.py` -- ReminderAgent**
Scheduled open-ticket nudge agent (shipped — registered in `main.py` when Zammad is available). Polls for tickets needing follow-up and routes a reminder notification via `NotificationRouter`. **`zammad_bot.py` -- ZammadBot**
Multi-stage AI triage pipeline for new, untagged tickets. Uses 4 system personas:
1. `triage_scout` → extract search keywords
2. Search Zammad for related closed tickets (global + per-user)
3. `triage_filter` → relevance scoring of historical tickets
4. `triage_summarizer` → compress long ticket bodies (adaptive, only if context exceeds limit)
5. `triage_analyst` → full analysis with context → internal note posted to ticket

**`managr_agent.py` -- ManagrAgent** (`agent_name="managr"`, DP-280/282/290)

**`sqlite_consolidator.py` -- SqliteConsolidator** (formerly `MemoryAgent`; `agent_name="memory"`)
Batch agent that segments conversations by topic, extracts observations via LLM, and stores embedded summaries. **Registered only when `SEMANTIC_BACKEND=="sqlite"`** — the Hindsight backend drives consolidation upstream, and registering this agent under it would crash `deploy()` on the first cycle (legacy SQL ops raise `NotImplementedError`). Two-phase pipeline per channel:

**Phase 1 — Embed (loop until no unembedded messages):**
1. `get_unembedded_messages()` fetches msgs not yet in Message_Embeddings
2. `_chunk_messages()` splits into token-aware batches (item cap + token cap)
3. `EmbeddingService.encode()` batch API call
4. INSERT into `Message_Embeddings` + `vec_Message_Embeddings`

**Phase 2 — Segment + Summarize (loop until clear):**
1. `get_unsegmented_embedded_messages()` fetches embedded msgs with `parent_summary_id IS NULL`
2. `_segment_by_similarity()` groups msgs by centroid-based cosine similarity (threshold from config, default 0.80)
   - Seeds centroid from tail of previous segment for continuity
   - Min segment size configurable (default **1**)
   - Bridging (two mechanisms):
     a. Explicit: msg has `reply_to_id` pointing to a message already in the current segment
     b. Heuristic: fallback for pre-`reply_to_id` data — single user msg immediately followed by assistant msg
3. `_summarize_segment()` sends transcript to LLM via `memory_summarizer` system persona
   - Token guardrail: counts tokens via Google SDK (`count_tokens`), skips segment if > `RATE_LIMIT_GEMMA_4_TPR * 0.95`
   - Pre-processes: strips vertexai grounding redirect URLs from content
   - LLM calls `submit_memory_summary` tool with `observations[]` + `keywords[]` + `outlier_ids[]`
   - Outlier msgs stay `parent_summary_id=NULL` for re-queueing in next batch
   - Fallback: parses plain text if model doesn't use tool call
4. Stores segment + summary + vec embedding in DB, sets `parent_summary_id` on processed msgs

Config in `agents.json`: similarity_threshold, min_segment_size, batch_size (default **100**, capped at 100), allowed_channels, embedding_provider
Rate limiting: shared `GLOBAL_EMBEDDING_LIMITER` (AsyncLimiter) with MemoryConsolidator to prevent double-spending embedding quota

### `src/app_manager.py` -- AppManager
Top-level lifecycle coordinator. Starts `agent_manager.auto_start()`, launches interface tasks (Discord, Gmail), blocks until every task finishes or shutdown is requested.

**Shutdown protocol (DP-304).** `start()` waits on `gather(*tasks, return_exceptions=True)` *and* a `_shutdown_requested` event, whichever comes first — `return_exceptions` so a crashing one-shot (`model_update` / `fixr_orphan_notify`) is logged rather than tearing down the interfaces with it. `request_shutdown()` is what SIGINT/SIGTERM reach, via `main._install_shutdown_handlers`; without it the only exit is `asyncio.run()`'s teardown, which cancels every task *before* `start()`'s `finally` runs, making the drain unreachable.

`shutdown()` is idempotent (`_shutdown_done`) and runs three phases:
1. **Signal, don't wait** — `agent_manager.signal_stop_all()` (agents share `MemoryManager._lock` with the consolidator, so they must stop *before* the drain, not after it), then each task's `stop=` callback. A `stop` may be sync or async; an awaitable return is awaited (`discord.py`'s `Client.close()` is `async def`).
2. **Cancel the uncooperative immediately** — a task registered without `stop=` was never signalled, so there is nothing to drain; waiting out the window would turn a ~0s shutdown into a 30s one.
3. **Drain cooperative tasks concurrently**, each against its own budget, then cancel the overruns and bounded-await the unwind.

Tunables: `GRACEFUL_SHUTDOWN_SECONDS` (30.0, default drain budget; override per task with `register_task(..., drain_timeout=)` when one work item can outlast it — `MemoryConsolidator.DRAIN_TIMEOUT_SECONDS` is 300.0 because its unit of work is a 31B summarizer call) and `CANCEL_GRACE_SECONDS` (5.0, bound on the post-cancel unwind; cancellation is a request, not a guarantee). Task names must be unique — they key the stop callbacks and drain budgets. A `drain_timeout` passed without a `stop=` callback is warned about. See decision `2026-07-30-interval-loop-shutdown-contracts` for drain-based vs cancel-based loop ownership.

### `src/proxmox/` -- Proxmox management subsystem (DP-262)
SSH-driven node/guest power ops + koboldcpp model swap on the GPU container's :5001 endpoint. Personas opt in via `service_bindings: ["proxmox"]`. The persona holding that binding is `hypr` (DP-327), which ships **unseeded** at `config/optional_personas/hypr.json` — an operator adds it to a specific instance's `data/personas.json` by hand. It is kept out of `default_personas.json` on purpose: `hypr` is the only persona exposing node power ops, and a park is approved by whoever raised it, so persona reachability *is* the authz boundary — seeding it would put that surface on every deploy. **DP-330 made that boundary enforceable rather than merely asserted**: `hypr` ships with an empty `origin_allowlist` (the guild id is the operator's and this repo is public) and the operator sets it on their own instance to pin `hypr` to one Discord guild. Accepted trade-off: an allowlisted `hypr` is Discord-only, so its parks can only be approved in Discord — letting the portal back in needs a transport-aware branch (portal auth is a `DERPR_CONTROL_TOKEN`, not a guild id), **not** a wildcard entry, which would grant every transport.
- `integration.py` — `ProxmoxIntegration(ServiceIntegration)` (name `"proxmox"`), registration-only. **Always** registers (even when `PVE_TOOLS_ENABLED` is false) so the startup-wiring contract holds; the handler short-circuits disabled calls with a clear error instead of attempting SSH.
- `handler.py` — `ProxmoxToolHandler` registers 8 tools; owns a config-driven `SSHRunner`.
- `ssh.py` — `SSHRunner` (config-driven host/user/key/timeout) runs remote commands as an **argv list** (never a shell string) via `asyncio.create_subprocess_exec("ssh", "-i", key, ...)`; `BatchMode=yes`, `ConnectTimeout`, hard `wait_for` timeout. `_reject_bad_args` refuses any arg containing shell metacharacters (defense-in-depth; only numeric vmids + config-pinned unit names ever pass). Transport failure/timeout → `SSHError`; a non-zero remote exit is returned, not raised.
- vmids are validated as digits; guest `kind` maps `ct→pct` / `vm→qm`. `set_active_model` disables every other **discovered** koboldcpp unit that binds `:5001` then `enable --now` the target (only one may hold the port). All executed on `PVE_MODEL_HOST_VMID` via `pct exec`.
- `_run` holds a `_MAX_INFLIGHT_SSH` semaphore. Every call is a fresh `ssh` process doing a full auth handshake (no `ControlMaster`), and the per-unit probes fan out over however many units the box happens to hold — a number DP-332 deliberately stopped bounding in config. Past sshd's default `MaxStartups` (10:30:100) connections start being dropped at random, so the cap sits at the one choke point every call passes through rather than at each fan-out site.
- Config: `PVE_TOOLS_ENABLED` (default-off; disabled → tools return a clear error, no SSH), `PVE_SSH_HOST` / `PVE_SSH_USER` / `PVE_SSH_KEY` / `PVE_SSH_TIMEOUT`, `PVE_MODEL_HOST_VMID` (CT101). Tool defs in `src/tools/tool_defs/proxmox.py`.
- Tools in `src/tools/tool_defs/proxmox.py` (`PROXMOX_TOOLS`, 8): read — `pve_status`, `list_models`, `gpu_status` (`exfil_capable=False`, no args); write (parked for confirmation) — `reboot_node` (also `irreversible`), `reboot_guest`, `start_guest`, `stop_guest`, `set_active_model`. All carry `produces_untrusted: False`, `locality: "network"`, `sensitivity: "internal"`.
- **Every write here is `exfil_capable: False` as of DP-265** (was: only `set_active_model`, DP-263). Honest, not convenient: the arguments are vmids, guest names and model keys *discovered from the node*, and the value that crosses SSH is always the resolved one — `_resolve_guest` matches a name locally and sends digits, `set_active_model` sends the discovered unit. The flag became load-bearing when DP-265 put untrusted HuggingFace reads on the same persona: without it, `ToolPolicy` Rule 2 sees untrusted reads in the `huggingface` domain beside network writes in the `proxmox` domain and quarantines `hypr`. The alternative — an `explicit_overrides` entry — would disarm Rule 2 for that persona's whole toolset permanently, including for tools nobody has written yet. `pve_status`/`list_models` keep the default `True`, which is what sets `has_network_read` so Rule 1 still fires if a local write is ever added. A future proxmox tool that genuinely carries a model-authored string out to the node **must not copy the flag**; pinned by `tests/test_tool_policy.py::test_every_proxmox_write_is_now_exempt_and_says_why`.
- ⚠️ **The node-side forced-command wrapper is the second half of every tool here** (`services/pve/derpr-pve-wrapper`, DP-267, versioned in-repo as of DP-265). sshd runs it instead of whatever derpr asked for, so a command shape the handler emits and the wrapper does not admit fails **in production and only in production** — a developer's own node key is unrestricted, so a live smoke test from a workstation proves nothing about the deployed path. DP-332 shipped `list_models` and `gpu_status` with three new shapes (`systemctl list-unit-files`, `ls /sys/class/drm`, `cat …/mem_info_vram_*`) and no wrapper update; unit tests, mypy and a live read-only smoke test all passed while both tools were dead on the deployed container. **Change an argv, change the wrapper in the same commit**, and verify with the container's key. `services/pve/README.md` has the deploy + verify steps.
- **Model-availability guard (DP-264):** `list_models` omits units whose gguf isn't on disk (a missing file can't be loaded, and enabling it would take :5001 down); `set_active_model` refuses the swap — leaving the current model running — unless the target's model file is present, so it never disables the live model to enable one that can't start (`_model_present` / `_unit_spec` in `handler.py`). `_unit_spec` parses one unit's `ExecStart` into `{model, port, contextsize, quantkv, readable}`; `_flag_value` accepts both `--flag value` and `--flag=value`, because systemd echoes `ExecStart` back verbatim and DP-332 is an invitation to hand-write units, and `_flag_int` coerces or drops. **`contextsize`/`quantkv` are published on each `list_models` row (DP-344)** — they are already in the tokens this call parses, so they cost no extra round trip, and they are the box's own *empirical* evidence about what the card holds: a unit that has been serving `:5001` at a given context has demonstrated that context fits, which outranks any figure derived from a gguf header. They are omitted rather than sent as null when the flag is absent, so "runs 163840" and "does not say" stay distinct.
- **Discovery-driven models (DP-332):** `_discover_units(vmid)` enumerates `systemctl list-unit-files --type=service` on the GPU CT and keeps whatever matches `_UNIT_RE` = `koboldcpp-([A-Za-z0-9._-]+)\.service`; the capture group is the friendly name. This replaced `PVE_MODEL_UNITS`, a config map that asserted what the box contained and drifted silently in both directions — DP-329 found the unit actually serving `:5001` unmapped, so `list_models` called every model inactive and no swap could succeed, with nothing erroring. It is also the prerequisite for DP-265: a freshly installed unit is reachable by `set_active_model` with no config edit and no redeploy. Four properties are load-bearing:
  - **The `koboldcpp-` anchoring happens in Python, not as a `'koboldcpp-*.service'` argument.** `ssh._reject_bad_args` forbids `*`, and pushing the glob remote would mean trusting the far-side shell to expand it as intended. `_UNIT_RE` is the *outer* bound on the set `set_active_model` disables — this is the one place discovery is *more* dangerous than the map was, since a loose match would take down something unrelated on the CT. Pinned by `test_set_active_model_disables_only_koboldcpp_units`, which seeds decoys (`nginx.service`, a bare `koboldcpp.service`, a `koboldcppx-` near-miss) into the default mocked listing.
  - **Discovered unit names are remote values that then travel back over SSH**, which the config map never did. `_UNIT_RE`'s character class is deliberately narrower than `ssh._FORBIDDEN` permits. `set_active_model`'s `name` argument stays a pure lookup key and never becomes an argv element — that is what keeps its `exfil_capable: False` claim true.
  - **The disable set is bounded by port, not by name (`_port_contenders`).** `_UNIT_RE` excludes names that aren't koboldcpp units at all, which was never the dangerous case: a *genuine* `koboldcpp-<name>.service` serving something else on another port — an embedding or draft server, a helper — matches the pattern perfectly, is not shown by `list_models`, and would be `disable --now`'d by every swap. The config map couldn't name one; discovery can. So `_unit_spec` parses each unit's `--port` (defaulting to koboldcpp's own `5001`, so "no `--port`" means *contends*), `list_models` publishes only the `:5001` units, and `set_active_model` disables only those — the shown set and the acted-on set stop diverging. A unit whose `ExecStart` can't be read counts as contending and is reported in the result's `warnings`: it may be the one holding `:5001`, and skipping it is how a swap "succeeds" while the old model keeps answering.
  - **Every disable's result is checked, and a failure aborts before the enable.** `systemctl disable --now` over `pct exec` can sit on a D-Bus job past `PVE_SSH_TIMEOUT` and get SIGTERM'd; the unit keeps `:5001`, and `enable --now` on a `Type=simple` target *still* exits 0, because "started" is not "bound". Discarding the disable results therefore reproduces the exact DP-329 silent failure this ticket exists to remove. The error says that units stopped before the failure stay stopped, so `:5001` may be serving nothing until a swap succeeds — an honest degraded state beats a false `active_model`.
- **`gpu_status` (DP-332):** reads `mem_info_vram_total` / `mem_info_vram_used` from the GPU CT's sysfs, returning total/used/free MiB per card. The card index is discovered from `ls /sys/class/drm` filtered by `_CARD_RE` (`card\d+`, so connector nodes like `card1-DP-1` and `renderD128` are excluded) — the live box exposes `card1`, so a hardcoded `card0` reads a path that does not exist. Rationale: DP-265 wants a VRAM budget before choosing `--contextsize`; the numbers are site-specific and must never be baked in (DP-328). **DP-337 moved the budget *formula* out of the persona prompt and into this tool layer** — the equation onto `install_model.contextsize` (the one argument it constrains) and the GTT-spill consequence onto this description; see `_kv_budget_note` below for the arithmetic itself. **There are two formulas, and the prompt has to keep them apart.** Growing the context of the model that is *already running* fits into free MiB. A swap does not: stopping the current unit releases everything it holds, so a `set_active_model` candidate is sized against total minus what stays resident. Sizing a swap against free MiB reads the live box (32624 total / 28601 used / 4022 free) as "nothing over 4 GiB fits" and refuses every swap there is — the failure mode the `hypr` prompt and the `gpu_status` tool description now both spell out. Free MiB is floored from the byte difference rather than from `total_mib - used_mib`, so the three can disagree by 1 MiB — overstating free VRAM is the direction that picks too large a context. Never raises: a dead CT, a missing sysfs path, or a non-amdgpu card comes back as an error dict or an entry in `errors`.
- **Guest inventory + name addressing (DP-327):** `_parse_table` turns a Proxmox fixed-width CLI table into row dicts keyed by its own lowercased header tokens, slicing at the header's column offsets. Header-driven rather than whitespace-split because `pct list`'s `Lock` column is usually **blank** — splitting on whitespace shifts `Name` into `Lock`'s slot — and because `pct list` and `qm list` disagree on both column set and order. The first field is anchored at column 0 so a right-aligned `VMID` wider than its header (`qm list`) is captured rather than truncated. Rows whose `vmid` isn't numeric are dropped, not guessed at.
  - `_guest_inventory()` gathers `pct list` + `qm list` concurrently into `{vmid, name, kind, status, lock}` dicts; one listing failing is reported in `errors` rather than aborting the other. `pve_status` returns this as `guests` **alongside** the raw text (which still carries columns the parse drops: mem, bootdisk, pid) — that structured field is what makes `pve_status` an infra-topology audit rather than two blobs to re-read each turn.
  - `_resolve_guest(vmid, name, kind)` accepts either address form. **The name is matched locally and never becomes an argv element** — only the resolved digits reach `SSHRunner`, which is precisely why `ssh.py`'s metacharacter guard remains a second line of defence rather than the only one. Pinned by `tests/proxmox/test_guest_lookup.py::test_name_never_crosses_the_ssh_boundary`.
  - `kind` is optional with a name (the lookup supplies it) and **required** with a bare `vmid` — an id alone doesn't say which CLI owns it, and guessing wrong on a power-off is not worth risking. Unknown names are refused with the list of names that exist; a name held by both a CT and a VM is refused as ambiguous until `kind` disambiguates.
  - Resolution runs at **execution** — after the park is approved — and the result carries a `target` block echoing the `vmid`/`kind`/`name` acted on, so the audit row records the resolved guest rather than only the argument the model typed. If **both** `name` and `vmid` are supplied they are cross-checked and a disagreement is refused: acting on the `vmid` while echoing the caller's `name` would put a guest we did not touch into the audit row and into the approval prompt the human read. A failed listing is reported as *not confirmable* rather than as "no such guest" — unknown and absent are different answers on a power path. `_resolve_guest` also short-circuits when `PVE_TOOLS_ENABLED` is false, so the disabled state reads as disabled instead of as an empty node.
  - The `_GUEST_PARAMS` schema marks nothing `required`; "one of name or vmid" is enforced in the handler because providers vary in whether they honour `anyOf`/`oneOf` in a function schema, and a constraint the provider silently drops is worse than none — it reads as enforced.

### `src/huggingface/` -- HuggingFace model provisioning (DP-265)
Find a gguf on the Hub and provision it onto the pve node, so it *becomes* a valid `set_active_model` target. Personas opt in via `service_bindings: ["huggingface"]`; the only one holding it is `hypr`, which also holds `proxmox` — deliberately the same blast radius rather than a new one. Sits **above** `src.proxmox` in the import-linter layer order because it reuses that package's `SSHRunner` instead of opening a second transport to the same node.
- `client.py` — `HFClient`: two read-only Hub calls (`/api/models?filter=gguf` search, `/api/models/<repo>/tree/<rev>` file listing), one `aiohttp` request each, no held session. `HFFile{path, size_bytes, sha256}`. `validate_repo_id`/`validate_file_path` gate every caller-supplied string *before* it is interpolated into a URL — percent-encoding a traversal yields a 404, and a 404 reads to a model as "try another spelling". `_as_gguf_file` prefers `lfs.size` over the top-level `size`: on a repo storing an uncommitted pointer the latter is ~135 bytes, and believing it would size the node's free-space precheck three orders of magnitude too small. An `lfs.oid` that isn't 64 hex (a git blob sha1) is dropped rather than passed through as a digest. `find_gguf_file` **refuses a file with no published sha256** — the digest is the only thing tying the bytes that land on the node to the bytes a human approved. Tree pagination follows `Link: rel="next"` up to `_MAX_TREE_PAGES`, so a sharded repo cannot decide how long a tool call runs.
- `handler.py` — `HuggingFaceToolHandler` registers 4 tools; owns an `HFClient` and shares the proxmox `SSHRunner`. Both injectable, so the whole feature tests with no network and no node.
- `integration.py` — `HuggingFaceIntegration(ServiceIntegration)` (name `"huggingface"`), registration-only, **always** registers so the startup-wiring contract holds.
- Config: `HF_TOOLS_ENABLED` (default-off), `HF_API_BASE`, `HF_API_TOKEN` (gated repos only), `HF_HTTP_TIMEOUT`, `HF_SEARCH_LIMIT_MAX`. Transport settings are the proxmox ones.
- Tools in `src/tools/tool_defs/huggingface.py` (`HUGGINGFACE_TOOLS`, 4): read — `hf_search`, `hf_files` (both `produces_untrusted: True`, `sensitivity: "public"`), `install_status` (`produces_untrusted: False`, explicit `domain: "proxmox"`, `exfil_capable: False`); write (parked) — `install_model` (explicit `domain: "huggingface"`).
- **The composition is the point.** Untrusted third-party reads sit beside node write access on one persona, so the invariant is *checked*, not assumed: the Hub reads and `install_model` share the `huggingface` egress domain, making `untrusted_read_domains == network_write_domains` — a same-origin closed loop that validates clean while leaving Rule 2 **armed** for anything added later. `install_model` is tagged `huggingface` even though derpr's own hop is SSH, because the payload it carries (the repo id) is what the node then fetches *from the Hub* — accurate tagging, not a dodge. `install_status` uses the same `capabilities["domain"]` seam in the opposite direction (`proxmox`), since its egress really is the node. This is the seam's first real user; it has existed unused since DP-128. Pinned by `tests/huggingface/test_hf_composition.py`, including a test that an added foreign-domain write still trips the rule.
- **What the model never decides.** (1) *What bytes land*: `install_model` reads the file's size and sha256 from the Hub itself and passes them to the node, which refuses on any mismatch. The enricher registered alongside the handler puts those same two values on the approval card, so a human approves a digest rather than a repo name — and an enricher failure returns loud `⚠️ UNVERIFIED` text rather than raising, because `ToolManager.enrich_audit_action` swallows exceptions into `None` and would render an ordinary-looking card that verified nothing. (2) *Where they land*: the node script owns the models directory and the unit template; no argument is a path. The Hub is re-read at execution, so a repo that changes the file between park and approval yields a different enforced digest — reported in the result rather than silently swapped.
- **`install_status` evaluates the KV budget rather than reciting it (DP-337).** `handler._kv_budget_note` turns the header's `n_layer` / `n_kv_head` / `head_dim` into bytes-per-token, the cache size at the installed `contextsize`, and the unit's total VRAM want (model buffer + KV + `_COMPUTE_BUFFER_MIB` 1010 + `_VRAM_MARGIN_MIB` 500). `bytes per element` is the constant ratio `_KV_BLOCK_BYTES 34 / _KV_BLOCK_ELEMS 32`, not a parameter, because `koboldcpp-model.service.in` hardcodes `--quantkv 1` and no tool exposes a knob for it — q8_0 stores a block of 32 quantised values in 34 bytes (32 int8 plus one f16 scale), so the cache is 1.0625 B/element. **DP-344 corrected this from `1`**, and the 6.25% shortfall had hidden because `n_layer` was simultaneously one too high on the model it was checked against: 17/16 is exactly 1.0625, so two errors cancelled to the right total for Qwen3.8-27B and to a wrong one for every other model. `n_layer` is now the count of layers that **cache** K/V, which on the hybrid architectures this host serves is a fraction of `block_count`. When the node determines the linear formula does not describe the model at all it sends `kv_shape_note` **instead of** the three numbers, and the note relays that reason and emits no arithmetic; a node older than DP-344 never sends it and degrades to the pre-existing "header did not publish" message. **The note is gated on `state == "done"`**: the node folds the header in only after the bytes verify, so an absent shape earlier means *not yet*, and reporting that as *unreadable* would be a worse answer than silence. Placement rationale is the general form of DP-335's root cause — a tool result arrives at the moment of need, costs nothing until called, versions with the code and is testable; a persona prompt is none of those, and here is hand-maintained on a docker volume so it does not even ship with the merge.
- **`install_status` re-publishes a whitelist**, not the node's document: `_STATUS_FIELDS` names every key and its type and truncates strings to 200 chars. That whitelist is what keeps the tool's `produces_untrusted: False` claim *enforced* — a future node-side change that started echoing an HTTP error body cannot quietly turn a trusted read into an injection surface.
- **The node side is the security boundary** (`services/pve/`, deployed by hand — see its README). One script, `/usr/local/sbin/derpr-model-install`, exposed as exactly one forced-command allowlist family (`install` and `status`; its `run` subcommand is invoked by systemd locally and is **not** admitted by sshd). derpr never gets `curl`, `systemctl`, or file writes as separate verbs. The script refuses before any bytes move on: an existing unit of that name, an existing file with a *different* sha256 (an identical one is reused), or insufficient free space (the larger of 2 GiB or 5%). ⚠️ **That last check guarded the wrong layer until DP-340.** It reads `df`, and it read it against `/srv/models` — a thin LV, where `df` reports the *volume's* free space and is structurally blind to the *pool* behind it running out. On 2026-08-21 it saw 75 GiB free over a pool with 14 GiB left, passed a 22 GB download, and put CT100 and CT101 into ext4 `emergency_ro` — taking zammad, the chatbot and hindsight's embedded postgres down together. Downloads now land on the **archive disk** (`/srv/archive/models`), an ordinary partition where `df` is the truth, so the pool is protected by not being written to rather than by a check. After download, a sha mismatch deletes the partial file and fails the job. Size and sha are **arguments**, not something the node re-derives — which also means the node needs no JSON parser, and a stock PVE node has no `jq`.
- **The unit lands disabled.** Installing does not put a model on `:5001` and does not disturb the running one; `set_active_model` is a separate call with its own approval. `contextsize` defaults to a deliberately small 8192 on the assumption a human tunes it against `gpu_status` first.
- **Long downloads run on the node, not in derpr.** `systemd-run --collect --unit=modelinstall-<job_id>` survives the SSH disconnect and derpr polls `install_status`. A background loop inside derpr was rejected: it re-opens the DP-304 interval-loop shutdown-contract problem for a job the node already supervises.
- **Hot/cold model tiering** (`services/pve/derpr-model-tier`, DP-340). Two tiers with the **cold one authoritative**: `/srv/models` on the SSD is what koboldcpp serves and holds a working set (~4-5 models, capped by `HOT_CAPACITY_BYTES`), while `/srv/archive/models` on the 1 TB archive HDD holds every gguf ever installed. `install_model` writes only to the archive; `set_active_model` promotes cold→hot on demand, evicting **least-recently-served** first, never a pinned model and never the one currently serving. Four things are load-bearing:
  - **Promotion is detached** (`systemd-run`, a job record polled through `install_status`) and returns `state: "promoting"` immediately. A 24 GB copy off a spinning disk is minutes, and a tool call held open that long is indistinguishable from a hung one — which an agent retries, racing two promotions for the same space (the DP-338 shape).
  - **Nothing is disabled while promoting.** `:5001` keeps serving until a second `set_active_model` swaps to the promoted file, so a failed promotion costs time and nothing else.
  - **Eviction never deletes a hot file without a verified archive copy** (present *and* sha-matching). That invariant is the only reason eviction is a cache operation rather than data loss.
  - **When pins leave no room the promotion fails and names them** rather than overruling one. A pin the system may override is not a pin. This is deliberately the *opposite* failure policy from the in-process LRU caps, which must always make room — recorded as a second LRU `by design` in `docs/capability_map.md`.
  - Free space is read as the **minimum of `df` and the thin pool's own free blocks** (`lvs data_percent`), for the reason in the paragraph above: on a thin LV, `df` alone is not a fact about whether a write can land.
  - **The handler degrades to pre-DP-340 behaviour when the node has no tier script** (`_tier_inventory` returns `{}`), because node artifacts and the container image are two independent deploys.
- `services/pve/gguf_header.py` (stdlib-only, deployed beside the installer) reads `n_layer` / `n_kv_head` / `head_dim` out of the downloaded gguf's header **and tensor index** and the installer folds them into the job status, so `KV_bytes_per_token = 2·n_layer·n_kv_head·head_dim·bytes_per_elem` can be *evaluated* rather than recited. It prefers a published `attention.key_length` over `embedding_length / head_count` — several architectures use a head dim that is not the quotient, and deriving it there understates the cache on exactly those models. **`n_layer` is counted off the tensor index — blocks carrying an `attn_k.weight` (or `attn_qkv.weight` for fused-QKV archs), less any block carrying `nextn.*` — and NOT from `block_count` (DP-344).** The two differ on every model this host serves: Qwen3.8-27B has 65 blocks of which 17 attend and 16 are cached (block 64 is its MTP draft layer, which koboldcpp only runs under the ROCm-only `--usemtp` that no unit here passes); Deckard-40B has 96 blocks and 24 cached. Using `block_count` overstated the cache 3.8-4x and produced a live answer of "32k is the maximum context" for a model that fits 262144. Validated to the byte against koboldcpp's own `llama_kv_cache: KV buffer size` on both. It also **refuses with a reason** (`kv_shape_note`) rather than estimating when the header says the cache is not linear in context: a per-layer `attention.head_count_kv` array (gemma4 publishes 16 on windowed layers, 4 on full-attention ones) or a published `attention.sliding_window`. That refusal required recording array values as markers instead of dropping them — an array that read back as absent made `head_count_kv or head_count` substitute gemma4's *query* head count, reporting ~2 MB/token. Unparseable input produces **no output and exit 0**: a header quirk must never fail an install whose bytes verified, and a partial shape yields nothing rather than a confident wrong number.

### `src/tools/mcp_client.py` + `mcp_integration.py` -- MCP client (DP-268)
Consume external MCP tool servers (streamable-HTTP transport). Discovered tools become ordinary derpr tools (`mcp__<server>__<tool>`, `service_binding: "mcp:<server>"`) — parking, taint, composition rules, and per-persona policy all apply with no MCP-specific downstream paths. Personas opt in per tool + bind `mcp:<server>` (no wildcard — see `dynamic` below).
- `mcp_client.py` — `MCPClientManager`, **owned by `main.py`** (voice precedent: `ServiceIntegration` is registration-only, so main.py owns the session lifecycle). Each server runs in a dedicated `_ServerConnection` task that owns the anyio transport contexts (must be entered/exited in one task); `_open_session` is the test seam. `start()` connects every enabled server from `MCP_SERVERS_FILE` (dead server logged + skipped, never breaks startup); `add_server` connects + discovers + registers the tools live and persists config **only on success** (rollback on failure; strict config load so a corrupt file is never clobbered); `remove_server` stops the session, unregisters defs + handlers, persists; `list_servers` reports url/enabled/connected/tools; `call_tool` invokes the server session. Every live (de)registration triggers `revalidate_persona_security` across all personas via `personas_provider`.
- **Translation** (`_translate_tool`): each discovered tool defaults to the most-restrictive metadata (`is_write: True`; `produces_untrusted`/`irreversible: True`, `locality: "network"`, `sensitivity: "pii"`), relaxable only by operator per-tool `tool_overrides` in the config file — server-provided annotations (`readOnlyHint`/`destructiveHint`/…) are logged as hints, never policy. Definitions carry **`dynamic: True`**, the marker that excludes them from `['*']` wildcard expansion in `ToolPolicy.filter_tools` (a new server can never silently widen or quarantine-cascade wildcard personas). Server name is validated, namespaced tool name capped at the 64-char provider limit, description capped at 1024 chars (prompt-injection surface).
- **Hot reload (phase 3):** a background maintenance loop reconnects dead servers and re-discovers a server's toolset when it signals `tools/list_changed` (the periodic tick is the fallback). Network work runs unlocked; registration swaps are all-or-nothing and a no-op when the toolset is unchanged (flap-safe). `MCP_RECONNECT_INTERVAL <= 0` disables the loop. While a server is down its tools stay registered and degrade to per-call `{"error": …}`, so persona policies stay stable across an outage.
- `mcp_integration.py` — `MCPIntegration(ServiceIntegration)` (name `"mcp"`), registration-only: attaches the `ToolManager` to the manager and registers the three management tools. **Always** registers (even when `MCP_ENABLED` is false) so the startup-wiring contract holds; disabled calls short-circuit with a clear error.
- Tools in `src/tools/tool_defs/mcp.py` (`MCP_TOOLS`, `service_binding: "mcp"`): `add_mcp_server` (`is_write` → parked; `url` is model-controlled egress, exfil-capable), `remove_mcp_server` (`is_write` → parked; `exfil_capable: False`), `list_mcp_servers` (read; `produces_untrusted: True`, `exfil_capable: False`).
- Live catalog: `ToolDefinitionRegistry` (`definitions.py`) holds discovered defs; `ToolManager.unregister` drops their handlers; discovered-tool handlers are closures over `MCPClientManager.call_tool`.
- Config (`global_config.py`): `MCP_ENABLED` (default off), `MCP_SERVERS_FILE` (default `DATA_DIR/mcp_servers.json`), `MCP_CONNECT_TIMEOUT` (30s), `MCP_CALL_TIMEOUT` (120s), `MCP_RECONNECT_INTERVAL` (60s). Dependency: `mcp` SDK.

### `src/tools/mcp_bridge.py` -- MCP **server** for dispatched subagents (DP-240)
Mirror of the MCP client above: derpr HOSTS an MCP server so a *capable* fixr subagent can call derpr tools. Mounted as a raw ASGI sub-app on the kobold adapter's FastAPI at `MCP_BRIDGE_PATH` (default `/mcp`); `StreamableHTTPSessionManager(stateless=True)`, whose task group is owned by the adapter's `_lifespan`.
- **Trust model (do not refactor away):** the server lives in the trusted derpr process; the subagent reaches it over HTTP across the sandbox. Deliberately NOT a stdio server spawned as a child of the agent's `claude` — a parent can subvert its own child, and the parent is the thing being gated. Capable dispatches keep `--dangerously-skip-permissions` (decided 2026-07-23), so **this module is the only authz boundary** — no defense-in-depth behind it.
- **Gating:** `_is_gated` = `is_write` OR `capabilities.irreversible` (independently sourced; fails closed on either). Gated → `propose_call` writes a `call_derpr_tool` proposal row and returns `{status: "parked_for_approval", proposal_id}` **without executing**; the tool description is annotated so the agent can plan around the park. Ungated → `runner.execute_ungated`. Dedup is safe: `create_proposal`'s ON CONFLICT clause is `WHERE ... ticket_number IS NOT NULL`, and agent calls carry no ticket, so each gets its own row.
- **Auth:** `BridgeTokenStore` mints one bearer token per capable dispatch (`resolve` compares constant-time across all live tokens). Verified in `handle_asgi` *before* the SDK is entered; the agent id is bound to a `ContextVar` the handlers read. `_handle_call` re-checks that binding as a fail-closed backstop — an unattributable call can't be gated or audited, so it must never run.
- Control-plane middleware exempts the bridge prefix **only when a bridge is mounted** (two principals, two credentials: operator `DERPR_CONTROL_TOKEN` vs per-dispatch bridge token) — not a standing hole on instances without one.
- `self_edit/dispatcher.py`: `dispatch(..., capable=False)`; capable mints a token, adds `--mcp-config` (http transport, token in the **header** not the URL) and appends the bridge host to sandbox `allowedDomains`. Capable-without-a-bridge is refused **before** `create_worktree` (a later refusal stranded an orphan worktree that nothing reaps — prune only walks registry rows). `answer_agent` reuses the SAME token (`token_for`) so a resumed agent keeps its tools; tokens revoked on DONE/ERROR/kill but **not** on QUESTION (a waiting agent is resumable).
- Config: `MCP_BRIDGE_ENABLED` (off), `MCP_BRIDGE_TOOLS` (**default-deny**), `MCP_BRIDGE_PATH`, `MCP_BRIDGE_PUBLIC_URL` (subagent's view; host auto-added to the sandbox allow-list). Wired in `main.py` §7.6 — the `AgentCallRunner` is built FIRST and shared with the proposal executor, so exposure and approval can't drift apart. Bridge-on + Zammad-off logs a warning: the review surface is unregistered, so gated calls would queue unapprovable.

### `src/proposals/` -- durable proposal queue (DP-282, managr Phase 1; self-managing queue DP-290)
Human-approval gating primitive for autonomous-agent writes — a **separate implementation** from `ConfirmationManager` (ADR 2026-07-04). ⚠️ The old justification — "that one is in-memory, one-pending-per-(user,persona), chat-turn-bound" — is **dead**: DP-297 made `ConfirmationManager` token-keyed and N-per-conversation, and DP-319 made it durable. What still separates them is `ProposalExecutor`'s `action_type` whitelist (arbitrary tool calls must not get a row it dispatches), nothing else. `ManagrAgent` proposes; a human approves via the portal; a separate executor writes. Documented in full in `docs/user_guide.md`.
- `schemas.py` — `PROPOSAL_ACTIONS` whitelist (`add_note` internal-only / `set_priority` / `remind`) + `validate_proposal_args` (required/type/enum/max_length/date, rejects unknown actions and unexpected keys). `build_submission_tool_schema()` derives the agent-internal `submit_proposals` tool from the whitelist.
- `executor.py` — `ProposalExecutor(zammad_client).execute(proposal) -> (bool, str)`. Re-validates args at execution time, resolves `ticket_number` → internal id via search, dispatches to the relevant Zammad write (add note / update priority / update state+pending_time). Errors returned, not raised.
- `service.py` — `ProposalIntegration(ServiceIntegration)`, `name="proposals"`; registers `list_proposals` (read), `approve_proposal`/`deny_proposal` (`is_write:True` → write gate). Approve reviews the row, audits, executes immediately, marks executed. Deny requires a reason. Lazy `expire_stale_proposals()` sweep on list/approve/deny. Registered in `main.py` only when Zammad is configured.
- Store: `Proposals` table in `memory_manager.py` — status pending/approved/denied/expired/executed/execution_failed/withdrawn; partial UNIQUE index on (agent, action_type, ticket_number) WHERE pending enforces dedup.
- Self-managing queue (DP-290): same-key pending proposal is UPSERTed in place instead of duplicated; `ManagrAgent` can also `reaffirm`/`revise`/`withdraw` its own pending proposals each cycle (reflective dispositions) — TTL acts as a GC backstop, not the primary lifecycle.
- Emission (in `ManagrAgent`): config-gated `proposals_enabled`; a second planner call with `tools=[submit_proposals]`; every candidate code-validated before insert, capped at `MANAGR_MAX_PROPOSALS_PER_CYCLE`.
- Standing orders (DP-281): the `Standing_Orders` table (`add`/`list`/`retire_standing_order`) holds operator-authored persistent instructions. Tools live on `StandingOrderToolHandler` (no executor dep) in `service.py`, same `proposals` binding; add/retire are audit-logged. `ManagrAgent` fetches orders **once per cycle** in `deploy()` (plan + extraction share the set), skips non-operator-source rows at injection, and on store failure prepends `STANDING_ORDERS_DEGRADED_NOTICE` to the digest + sets `standing_orders_degraded` in the outcome (fail-open is operator-visible). `MANAGR_STANDING_ORDERS_LIMIT` (20); `list_standing_orders` raises on limit<1 (SQLite `LIMIT -1` is unbounded) and caps at 200.
- **Subagent tool calls (DP-240):** `AGENT_CALL_ACTIONS` (`call_derpr_tool`: tool_name/tool_args/agent_id) is a **separate dict** from `PROPOSAL_ACTIONS`, and `EXECUTABLE_ACTIONS` is the union. Reason: `build_submission_tool_schema` enum-pins to `PROPOSAL_ACTIONS`, and managr reads attacker-reachable ticket text — a generic tool-call action in that dict would let a poisoned ticket steer managr into proposing arbitrary derpr calls. `validate_proposal_args(scope=...)` defaults to `PROPOSAL_ACTIONS` so every pre-existing caller stays fail-closed; only `ProposalExecutor` passes `EXECUTABLE_ACTIONS`.
- `agent_call.py` — `AgentCallRunner(tool_manager_lookup, policy_lookup)` (closures, not bound refs: the engine rebinds `tool_manager`). `exposed_tool_definitions()` = registered-handlers ∩ bridge `ToolPolicy` (one source for both `tools/list` and the execute-time check, so listing and execution can't disagree). `run()` **re-derives exposure at execution time** and refuses a stale row — the property that makes an indefinitely-queued approval safe. `execute_ungated()` is the immediate path for read tools. `executor.py` gains an optional `agent_call_runner`: `call_derpr_tool` short-circuits before ticket resolution; a `None` runner refuses loudly, never silently "executed".
